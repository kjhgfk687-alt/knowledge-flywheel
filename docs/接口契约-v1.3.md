# 知源（KnowSource）`/retrieve` 接口契约 v1.0

> 接口定位：知源（项目A，多租户商户知识运营平台）暴露，客舟（项目B，电商客服智能体）调用。
> 这是客舟消费知识的**唯一入口**，也是飞轮的起点：检索结果的 `query_id` 预留给后续"转人工→审核理由回写案例库"接口做链路关联。
> 两个项目分别开会话开发，本文件是双方共同依据，任何修改必须双方会话同步。

---

## 1. 接口基本信息

| 项 | 值 |
|---|---|
| HTTP 方法 | `POST`（query 为中文长文本，放 body，避免 URL 长度与转义问题） |
| 路径 | `/api/v1/retrieve` |
| 请求 Content-Type | `application/json; charset=utf-8` |
| 响应 Content-Type | `application/json; charset=utf-8` |
| 知源 Base URL（开发环境） | `http://localhost:8100`（端口约定：知源 8100，客舟 8200，避免冲突） |
| 鉴权 | 请求头 `X-API-Key`：服务间共享密钥，双方 `.env` 配置同一值（开发环境约定占位：`zs-kz-dev-key-001`）；租户身份由请求体 `tenant_id` 声明 |

鉴权演进预留（不影响本契约字段）：
- 阶段一：单一共享密钥 + body 声明 `tenant_id`，不做 key↔tenant 绑定，不做 OAuth。
- 阶段三（可选）：每租户独立 API Key，服务端校验 key 归属租户，防横向越权。仅服务端校验增强，接口签名不变。

## 2. 请求体（Request）

| 字段 | 类型 | 必填 | 默认值 | 含义 | 约束 |
|---|---|---|---|---|---|
| `tenant_id` | string | 是 | — | 租户 ID，检索范围隔离的根 | 正则 `^[a-z0-9][a-z0-9_]{1,31}$`，总长 2–32 |
| `query` | string | 是 | — | 检索查询（客舟的原始用户问题或改写后的问题） | 去首尾空白后非空，1–512 字符 |
| `top_k` | int | 否 | 5 | 返回证据条数上限 | 1–20 |
| `filters` | object | 否 | `null` | 结构化过滤条件，条件之间为 AND | 只允许下述两个键，未知键报错 |
| `filters.category` | string[] | 否 | `null`（不过滤） | 商品品类，如 `["箱包", "手表"]` | 元素为非空字符串，数组长度 ≤ 10 |
| `filters.auth_status` | string[] | 否 | `null`（不过滤） | 鉴定状态过滤 | 元素枚举：`authentic` / `fake` / `unknown` |
| `include_platform` | bool | 否 | `true` | 是否包含平台层知识（平台政策、通用流程规范） | — |
| `include_case` | bool | 否 | `true` | 是否包含案例知识（客舟转人工后回写沉淀的审核案例） | 预留为飞轮效果的 A/B 开关（关掉案例库对比转人工率变化） |

语义说明：
- `filters` 传 `null` 与缺省等价；传空数组 `[]` 视为非法（与"不过滤"语义冲突），返回 422。
- `include_platform=false` 且 `include_case=false` 合法：只检索该商户自己的文档层。
- 案例知识归属租户隔离空间内（每个商户自己的案例库），`source_type=case`。

## 3. 响应体（Response）

### 3.1 统一信封（成功与错误同构）

```json
{
  "code": 0,
  "message": "ok",
  "data": { ... }
}
```

成功时 `code=0`；错误时 `code` 为非 0 错误码、`data=null`（见第 4 节）。

### 3.2 成功 `data` 结构

| 字段 | 类型 | 含义 |
|---|---|---|
| `query_id` | string | 本次检索唯一 ID（`ret_` 前缀）。用于日志追踪，并预留给回写接口关联"检索→转人工→审核理由"链路 |
| `tenant_id` | string | 回显请求的租户 ID（客户端防串租户校验用） |
| `retrieved` | bool | **检索为空的显式标识**。`false` = 检索正常执行但无相关证据（不是错误）；客户端不得只凭 `evidence==[]` 判断 |
| `degraded` | bool | 是否走了降级检索路径 |
| `degrade_reason` | string \| null | 降级原因枚举：`vector_store_unavailable` / `embedding_failed` / `vector_timeout`；未降级时为 `null` |
| `total` | int | `evidence` 数组长度（0 ≤ total ≤ top_k） |
| `evidence` | Evidence[] | 证据列表，**三层来源合并为一个数组，按 score 降序** |
| `latency_ms` | int | 服务端总耗时（毫秒），客舟侧用于监控对比正常/降级路径 |

### 3.3 Evidence 单条结构

| 字段 | 类型 | 必有 | 含义 |
|---|---|---|---|
| `chunk_id` | string | 是 | 全局唯一切片 ID（`chk_` 前缀） |
| `content` | string | 是 | 切片正文全文（阶段一切片不超过 500 tokens，不做二次截断） |
| `source_type` | string | 是 | `platform` / `merchant` / `case` |
| `source_title` | string | 是 | 来源文档标题 / 案例标题 |
| `score` | float | 是 | 相关性得分 0–1，保留 4 位小数。正常路径 = 向量余弦相似度；降级路径 = 关键词相关性归一化分 |
| `metadata` | object | 是 | 按 `source_type` 不同，见 3.4 |

### 3.4 metadata 字段（按 source_type）

公共字段（三种来源都有）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `doc_id` | string | 来源文档 ID |
| `chunk_index` | int | 切片在文档内的序号（0 起） |
| `created_at` | string | 入库时间，ISO 8601 |

`merchant` 额外：`category`（string \| null）商品品类。

`platform` 额外：`effective_date`（string \| null）平台政策生效日期。

`case` 额外：

| 字段 | 类型 | 含义 |
|---|---|---|
| `case_id` | string | 案例 ID（回写接口的主键，预留） |
| `original_query` | string | 当初触发转人工的原始用户问题 |
| `review_result` | string | 人工审核结论摘要（即飞轮回写的"审核理由"） |
| `hit_count` | int | 该案例被检索命中的累计次数（飞轮核心指标：命中越多说明沉淀越有效） |
| `feedback_source` | string | 回写来源系统，当前恒为 `kezhou` |

### 3.5 设计决策：合并返回，服务端按层优先级排序（v1.3 终态）

**结论：三层证据合并为单一 `evidence` 数组返回，顺序由知源服务端的分层排序策略决定——案例层证据优先命中（飞轮核心），商户层证据其次，平台层证据作为兜底约束附在最后；各层内部按 score 降序。`score` 只保证层内降序，不保证全局降序。**

理由：
1. 分三个数组会让客户端写合并排序逻辑，两项目两处实现容易漂移；单一数组 + `source_type` 携带层级，客户端需要分组时信息无损。
2. 排序即语义：客舟按数组顺序注入 prompt，就天然实现"类似问题优先命中案例、商户层证据回答具体商品问题、平台层证据附末尾兜底"的冲突处理规则。

排序策略细则：
- `include_case=false`：商户层查询完全排除案例切片（飞轮 A/B 度量开关：关掉案例库对比转人工率）。
- `include_platform=true` 且平台层存在相关证据时，平台层**保留最后一个席位**（`top_k ≥ 2` 时）；案例层与商户层分享其余名额，案例优先。
- `total` 永远不超过 `top_k`。
- 案例命中即累计 `hit_count`（响应 metadata 中为命中后的最新值）——飞轮核心指标。
- 平台层知识全商户共享；`platform` 为保留标识，**不能**作为 `tenant_id` 传入（返回 40001）。

## 4. 错误码

统一错误信封：

```json
{ "code": 40002, "message": "query 为空或超长（1-512 字符）", "data": null }
```

| HTTP | code | 错误标识 | 场景 |
|---|---|---|---|
| 401 | 40100 | `AUTH_KEY_MISSING` | 未携带 `X-API-Key` 请求头 |
| 401 | 40101 | `AUTH_KEY_INVALID` | `X-API-Key` 值不正确 |
| 422 | 40001 | `TENANT_ID_INVALID` | `tenant_id` 缺失 / 格式非法（不满足正则或长度） |
| 422 | 40002 | `QUERY_INVALID` | `query` 缺失 / 去空白后为空 / 超 512 字符 |
| 422 | 40003 | `TOP_K_INVALID` | `top_k` 非整数或超出 1–20 |
| 422 | 40004 | `FILTERS_INVALID` | `filters` 含未知键 / 传空数组 / 枚举值非法 / 结构非对象 |
| 422 | 40005 | `BODY_NOT_JSON` | 请求体不是合法 JSON 或 Content-Type 不符 |
| 404 | 40401 | `TENANT_NOT_FOUND` | `tenant_id` 格式合法但租户不存在（注意与 40001 区分） |
| 403 | 40301 | `TENANT_DISABLED` | 租户被禁用（预留，阶段一可不实现该校验） |
| 503 | 50301 | `RETRIEVAL_UNAVAILABLE` | 向量检索与关键词降级路径**均**失败 |
| 504 | 50401 | `RETRIEVAL_TIMEOUT` | 总耗时超预算（含降级尝试，默认 3s）仍未返回 |
| 429 | 42901 | `RATE_LIMITED` | 触发限流（预留，阶段二启用） |
| 500 | 50000 | `INTERNAL_ERROR` | 未分类内部错误 |

`message` 规则：中文一句话，面向开发者可定位，参数类错误须带出具体原因（如 `tenant_id 格式非法: 期望 ^[a-z0-9][a-z0-9_]{1,31}$`）。

实现注记（影响可观测行为，双方需对齐）：FastAPI 参数校验默认返回 422 + 自有错误结构，知源侧须用异常处理器把所有错误统一改写为本契约信封，客舟**只按本表解析**。

## 5. 降级行为

**结论：降级返回，不报错。**

触发条件（满足其一即降级）：
1. 向量库连接失败 / 不可用；
2. query 向量化（embedding 调用）失败；
3. 向量检索超时（内部预算 800ms）。

降级行为：
- 自动切换**关键词检索**（实现：PostgreSQL 全文检索，jieba 应用层分词、OR 连接查询偏召回，对切片文本匹配），走完相同的过滤逻辑（`filters` / `include_platform` / `include_case` 全部生效）；
- 返回 **200 + 正常信封**，并置 `degraded=true`、`degrade_reason` 为对应枚举值；
- `score` 语义变为关键词相关性归一化分（0–1），字段结构不变；
- 客舟侧消费约定：收到 `degraded=true` 时应下调自身置信度评估（更倾向转人工）——知识库故障产生的 case 恰好继续喂飞轮，故障被链路吸收而不是击穿会话。

二级失败：
- 关键词降级路径也失败 → 503 `50301`；
- 总耗时超 3s（向量尝试 + 降级尝试）→ 504 `50401`。

注意：**检索为空不是降级**（`retrieved=false, degraded=false`）；**降级后检索为空也是合法响应**（`retrieved=false, degraded=true`），只有"两条路径都跑不了"才报错。

## 7. 回写接口：`POST /api/v1/cases`（v1.3 新增，飞轮沉淀端）

飞轮闭环的另一半：客舟转人工 → 人工审核写理由 → **本接口回写知源** → 管理员确认后进入案例知识库（半自动：入库前必经人工确认，确认时可修订结论）。

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST /api/v1/cases` |
| Content-Type | `application/json; charset=utf-8` |
| 鉴权 | 同 §1：`X-API-Key` 请求头 |
| 知源 Base URL | 同 §1：`http://localhost:8100` |

### 7.1 请求体

| 字段 | 类型 | 必填 | 默认值 | 含义 | 约束 |
|---|---|---|---|---|---|
| `tenant_id` | string | 是 | — | 案例归属租户 | 同 §2 正则 |
| `original_query` | string | 是 | — | 触发转人工的原始用户问题 | 去空白后非空，1–2000 字符 |
| `review_result` | string | 是 | — | 人工审核结论（飞轮回写的"审核理由"） | 去空白后非空，1–2000 字符 |
| `query_id` | string | 否 | `null` | 关联的原始检索（§3.2 返回值），链路追踪键 | `ret_` 前缀；知源不校验存在性 |
| `category` | string | 否 | `""` | 商品品类 | ≤ 64 字符 |
| `feedback_source` | string | 否 | `kezhou` | 回写来源系统标识 | ≤ 32 字符 |

### 7.2 响应

成功（200）返回信封 `code=0`，`data` 为案例对象：

```json
{
  "code": 0,
  "message": "案例已接收，待确认后进入案例知识库",
  "data": {
    "case_id": "case_541ec359b457",
    "tenant_id": "t_bagshop_001",
    "query_id": "ret_demo0001",
    "original_query": "……",
    "review_result": "……",
    "category": "箱包",
    "status": "pending",
    "hit_count": 0,
    "feedback_source": "kezhou",
    "created_at": "2026-09-22T11:20:26Z",
    "confirmed_at": null
  }
}
```

关键语义：回写只产生 **pending** 案例，**确认入库前不可被检索命中**。确认/修订/驳回是知源控制台的人工操作（非本契约范围）；案例元数据中的 `hit_count` 每次被检索命中 +1。

### 7.3 错误码

复用 §4：401/40100-40101（鉴权）、422/40001（tenant_id 非法）、422/40002（`original_query`/`review_result` 为空或超 2000 字符）、422/40004（未知字段、`query_id` 非 `ret_` 前缀）、404/40401（租户不存在）、403/40301（租户被禁用）。

### 7.4 客舟侧调用时机建议

转人工 case 的人工审核结论落定后调用；`query_id` 务必携带当次 `/retrieve` 返回值，形成"检索→转人工→回写"的可追踪闭环。
