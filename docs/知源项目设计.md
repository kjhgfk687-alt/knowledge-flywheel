# 知源（KnowSource）项目结构设计与阶段一模块拆分

> 前置依据：[知源retrieve接口契约 v1.0](知源retrieve接口契约.md)（已双方确认）。
> 本文是知源开发的实施蓝图，确认后按模块逐个交付，不一次性生成所有代码。

---

## 1. 技术选型定案

| 决策点 | 选择 | 理由 |
|---|---|---|
| 向量库 | **ChromaDB（embedded 模式）** | `pip install` 即用、无独立服务、本地目录持久化、原生 metadata 过滤（tenant_id/layer）、LangChain 集成成熟。pgvector 虽复用 PG，但 Windows 下扩展管理繁琐；Chroma 更符合"部署简单优先"。预留迁移路径：检索层走 VectorStore 接口，数据源头在 PG，可随时重建索引 |
| RAG 框架 | **LangChain（只用组件）** | 只用其 TextSplitter 等组件，检索路径为手写 service 代码、不用 chains。与客舟的 LangGraph 同生态，简历叙事一致；避免框架锁死检索核心 |
| Embedding | **fastembed + BAAI/bge-small-zh-v1.5**（本地 ONNX，512 维） | 中文效果好、无需 GPU、无 API 依赖（降级路径可本地自测）、免装 torch（比 sentence-transformers 轻一个数量级）。EmbeddingProvider 接口化，可切 OpenAI 兼容 API |
| ORM | **SQLAlchemy 2.0（同步）+ Alembic** | 阶段一规模下同步最简、好调试；FastAPI 自动走线程池。后续二/三阶段 schema 会变，Alembic 从第一天接管 |
| PDF 解析 | **pypdf** | MIT 协议、纯 Python、够用 |
| 关键词降级 | **PostgreSQL 全文检索（jieba 分词 + tsvector + GIN）** | 契约原文写的是 SQLite FTS5，但 PG 已在栈内，再用 SQLite 等于引入第二个存储引擎 → 提契约小改（见 §2）。中文分词用应用层 jieba 预分词 + `simple` 配置，避开 Windows 上装 pg_jieba/zhparser 的坑 |
| 前端 | **Vue 3 + Vite + Element Plus + Vue Router + Axios**（不上 Pinia） | 两页应用无全局状态需求，保持最简 |
| 基础设施 | **docker-compose 只起 PostgreSQL** | Chroma embedded、fastembed 本地跑，无其他服务。端口：后端 8100（契约）、前端 5173、PG 5432 |

## 2. 与已确认契约的对齐点（3 项）

1. **需契约小改（v1.0 → v1.1，一行）**：第 5 节降级实现 "SQLite FTS5" → "PostgreSQL 全文检索"。对外行为（degraded 标识、字段、语义）完全不变，仅实现载体更合理——PG 本来就是事实源，避免双存储同步。**待你确认后我改契约文件并记变更**。
2. **溯源卡片字段：契约已覆盖，无需改动**。卡片每个 UI 元素 ↔ 契约字段映射：来源徽标=`source_type`、标题=`source_title`、正文=`content`、相关度条=`score`、出处脚注=`metadata.doc_id + chunk_index + created_at`、案例卡额外展示 `original_query / review_result / hit_count`。
3. **阶段二排序演进预告**：你定义的冲突规则（商户层证据优先回答、平台层证据附在上下文末尾兜底）落在知源侧 = 排序策略变为 **案例 → 商户 → 平台**（层内按 score），客舟按返回顺序注入 prompt 即天然实现兜底约束。阶段一只有商户层、纯 score 排序，与契约 v1.0 完全一致；到阶段二改排序时按契约预留的演进方式（新增可选字段 + 变更记录）升级 v1.2，届时通知客舟会话。

职责边界备注：「对话记忆按租户隔离」属于客舟（LangGraph checkpointer 以 tenant 为 key），知源只负责**检索隔离**——向量查询与关键词查询都强制带 tenant 过滤。

关键边界约定：
- **`/api/v1/retrieve` 是客舟唯一可调用的端点**；`/api/v1/documents/*` 是知源前端控制台的内部 API，不属于契约，用 OpenAPI 文档自描述。阶段一控制台 API 不做鉴权（dev 模式），阶段三加管理员登录时再收口。
- Chroma 是**可重建的索引**，PG 是**事实源**（chunk 正文存 PG）。索引损坏可从 PG 全量重建——这也是降级路径天然成立的原因。

## 4. 数据模型（阶段一 3 张表，含前瞻字段）

| 表 | 字段（阶段一） | 说明 |
|---|---|---|
| `tenants` | `id` PK, `tenant_id` UNIQUE, `name`, `status`(active/disabled), `created_at` | 撑起 40401/40301 校验；seed 两个租户 |
| `documents` | `id` PK, `tenant_id` FK, `layer`(merchant/**platform**), `title`, `file_name`, `file_type`(pdf/md/txt), `status`(uploaded/parsing/indexed/**failed**), `error_msg`, `chunk_count`, `created_at` | `layer` 字段**现在就建、阶段一只用 merchant**，阶段二加平台层零迁移；failed 状态显式落库，摄取失败前端可见 |
| `chunks` | `id` PK, `chunk_id` UNIQUE(契约 `chk_` ID), `document_id` FK, `tenant_id`, `layer`, `chunk_index`, `content`, `content_fts`(jieba 预分词, tsvector, GIN 索引), `meta` JSONB, `created_at` | `content_fts` 摄取时写好，降级路径零准备成本 |

阶段三再加 `cases` / `review_records` 表，本阶段不建。

## 5. 阶段一模块拆分（M1–M8）

| 模块 | 内容 | 关键交付 | 完成标志 |
|---|---|---|---|
| **M1 骨架与错误信封** | FastAPI app、config、契约 §4 全部错误码的信封实现与全局异常处理器、`/healthz` | `main.py` `config.py` `core/errors.py` | curl 一个不存在的路径也返回契约信封 |
| **M2 存储层** | docker-compose(PG)、SQLAlchemy 模型、Alembic 初始迁移、seed 脚本 | `infra/db.py` `models.py` `scripts/seed.py` | seed 后 psql 可查 2 租户；GIN 索引存在 |
| **M3 向量与嵌入层** | EmbeddingProvider（fastembed 实现 + 接口）、Chroma 封装（upsert / 带 tenant+layer 过滤查询） | `infra/embedder.py` `vector.py` | 单测：同文本相似度≈1，跨文本低 |
| **M4 摄取管道** | 上传端点（multipart，pdf/md/txt）、解析、RecursiveCharacterTextSplitter（默认 400 字/重叠 50，保住 bge 512 token 上限）、双写 PG+Chroma、status 状态机（失败显式落库） | `api/documents.py` `services/ingest.py` | UI/API 上传 md+pdf → status=indexed，chunk 预览正确 |
| **M5 检索服务** | 向量路径（过滤+top_k）→ 800ms 内部超时/失败捕获 → PG FTS 降级（ts_rank→0-1 归一化）→ Evidence 组装、query_id、latency、retrieved/degraded 标识 | `services/retrieval.py` `infra/keyword.py` | 正常与降级两条路径单测均绿 |
| **M6 契约端点** | `POST /api/v1/retrieve`：X-API-Key 校验、请求校验（422 族错误码）、响应按契约信封 | `api/retrieve.py` `schemas/retrieve.py` | 手工 curl 对齐契约 §6 三个示例响应 |
| **M7 前端两页** | 知识管理页（租户切换、上传、状态列表、切片抽屉预览）+ 检索测试页（query/top_k/filters/开关、EvidenceCard 溯源卡片、空态与降级态显式展示） | `frontend/` 全部 | 浏览器完成"上传→检索→看卡片"演示 |
| **M8 测试与验收** | 契约一致性测试（§4 每个错误码 + §6 响应结构断言）、round-trip、降级（mock Chroma 故障）、隔离（A 租户查不到 B 的内容） | `tests/` | pytest 全绿 + 一条手工演示路径 |

**实施顺序**：M1 → M2 → M3 → M4 → M5 → M6 → M8 → M7（前端最后，接口稳定后写 UI 最省返工）。每个模块单独交付、单独验证，不一次性生成。

**明确不在阶段一范围**：平台层检索（表结构已预留）、案例库与回写接口、限流、租户级 API Key 绑定、管理员登录、文档删除/重建索引（列表+上传+预览先行）。

## 6. 阶段一验收标准（可演示）

1. seed 两个租户，各上传不同文档；
2. 检索测试页用租户 A 提问 → 返回契约结构 evidence，溯源卡片字段齐全；
3. 切换租户 B 同样提问 → 看不到 A 的任何内容（隔离）；
4. 提一个库里没有的问题 → `retrieved=false` 空态卡片，不编造；
5. 停掉/故障注入 Chroma → `degraded=true` 仍有结果（PG FTS 兜底）；
6. 缺 API-Key、空 query、非法 tenant_id → 分别命中 401/422 对应错误码；
7. `pytest` 全绿。
